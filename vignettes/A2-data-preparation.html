Data Preparation for National FADN and LPIS

Overview

National FADN databases may differ from the EU FADN in three ways:

  1. Table structure — National FADNs may use long product tables (one row per farm × product) while the EU FADN is a single wide table (one row per farm).
  2. Variable naming — Different suffixes encode the same concept (e.g., SUPER3 in French FADN = TA in FADN = total area).
  3. Category codes — Products are identified by national codes (e.g., French FADN code 111 = FADN code CWHTC).

The conversion is driven by three user-filled tables:

Table What it maps Example
Variable pattern Suffix ↔︎ suffix within a product group SUPER3 → TA (total area, CROPS)
Category pattern National product code → FADN product code 111 → CWHTC (common wheat)
Manual matches National code of farm level variable → FADN code AGBIO → ORGANIC (organic farming certification)

Together they generate the full variable mapping: national long-table column SUPER3 for code 111 becomes wide-table column CWHTC_TA.

Understanding the three conversion tables

Variable pattern table

Each row maps one variable suffix in the national FADN to one variable suffix in the EU FADN, within a product group. Some FADN suffixes have no national equivalent (and vice versa) — these rows are left with the corresponding cell empty.

Here is the structure the user must fill:

Column Description Example
pattern_FADN EU FADN variable suffix TA
description_FADN Description of the EU FADN variable Total area under production
comment_fadn EU FADN unit or clarification in ha
Group Product group: CROPS, LIVESTOCK, or ANIMAL PRODUCTS AND SERVICES CROPS
pattern_national National (RICA) suffix in the long table SUPER3
description_national Description of the national variable Surface
comment_national National unit or clarification are
unit_conversion Conversion factor from national to EU unit: national_value × unit_conversion = fadn_value (1 if same unit) 0.01 (are → ha)

Key observations from the RICA example:

  • Some FADN suffixes have no RICA equivalent (e.g., livestock suffixes like SSN, SSV, SRN, SRV). These are left with an empty pattern_national cell.
  • Some RICA suffixes have no FADN equivalent — these can be included with an empty pattern_FADN cell if the user wants to preserve them.
  • The Group column determines which raw table and code column to use:
  • CROPS → table veg, code column CODE3
  • LIVESTOCK → table ani, code column CODE6
  • ANIMAL PRODUCTS AND SERVICES → table pan, code column CODE7

Category pattern table

Each row maps one national product code to one FADN product code. When several national codes map to the same FADN code, they will be summed during aggregation (many-to-one). When one national code maps to several FADN codes, an allocation key is needed (one-to-many).

Column Description Example
FADN_code_letter EU FADN product code CWHTC
national_code National product code (semicolon-separated if multiple) 111
Group CROPS, LIVESTOCK, or ANIMAL PRODUCTS AND SERVICES CROPS
allocation_key Allocate values from one national code to multiple FADN codes (values must sum to 1 for each national code) 076 = eggs in French RICA matches with PEGGC and PEGGH in EU FADN

Note: When multiple national_code rows share the same FADN_code_letter, the corresponding pivoted columns are summed. For example, RICA codes 115 and 116 both map to CBRL (barley), so 115_SUPER3 + 116_SUPER3 → CBRL_TA. Conversely, when one national_code row match with multiple FADN_code_letter, the national columns is allocated to the different corresponding pivoted columns according to the allocation key provided (allocation_key). For example, RICA code 076 map to PEGGC and PEGGH, so 076_QPROD7 → PEGGC_PRQ + PEGGH_PRQ.

Manual matches table

The manual_matches sheet handles farm-level variables that do not follow the prefix–suffix logic of the category_pattern and variable_pattern sheets. These are typically variables stored directly in the main farm table (e.g., the French rica table) rather than in product-specific tables (veg, ani, pan). Examples include geographic identifiers, farm typologies, fuel and electricity consumption, mineral fertiliser use, and purchased feed values. Step-by-step workflow

Step 1 – Load raw national data

We will use the French RICA as an example. In the French RICA, we have several tables: a farm-leval variable table and tables for products (crops, animals, animal products).

We gather the table in one list with the following structure:


data("mock_data")

  rica = mock_data$rica_fict$rica,
  veg  = mock_data$rica_fict$veg,
  ani  = mock_data$rica_fict$ani,
  pan  = mock_data$rica_fict$pan
)

RICA_19_raw <- list(
  rica = mock_data$rica_fict$rica,
  veg  = mock_data$rica_fict$veg,
  ani  = mock_data$rica_fict$ani,
  pan  = mock_data$rica_fict$pan
)

RICA_18_raw <- list(
  rica = mock_data$rica_fict$rica,
  veg  = mock_data$rica_fict$veg,
  ani  = mock_data$rica_fict$ani,
  pan  = mock_data$rica_fict$pan
)

National FADN data typically arrive as separate files per year. The package provides stack_yearly_tables() to bind them into a single set of tables before pivoting.

Step 1.1 — Load each year’s raw data

# Suppose you have raw RICA data loaded per year:
# RICA_18_raw, RICA_19_raw, RICA_20_raw — each a named list of data frames
# with elements like "rica", "veg", "ani", "pan", "tvn", "res", ...

yearly_data <- list(
  "2018" = RICA_18_raw,
  "2019" = RICA_19_raw,
  "2020" = RICA_20_raw
)

Step 1.2 — Stack into combined tables

raw_tables <- h_stack_yearly_tables(yearly_data, year_col = "YEAR")
# Stacked 4 tables across 3 years.
#   rica: 22500 rows (3 years)
#   veg:  185000 rows (3 years)
#   ani:  67000 rows (3 years)
#   ...

Each table in raw_tables now has a YEAR column. You simply include it in id_cols so that each farm × year combination stays on its own row.

Notes on multi-year stacking

  • Column consistency: stack_yearly_tables() uses dplyr::bind_rows(), which handles columns that appear in some years but not others (filled with NA). If a variable was renamed between survey years, harmonise the column names before stacking.

  • Year-specific unit changes: If units changed between years (e.g., areas switched from ares to hectares in 2019), pre-process the affected tables before stacking to match the unit_conversion variables registered in your dictionary

  • Table naming: When stacking, the table names in the combined list must match those referenced in table_config. If your yearly files use year-suffixed names (e.g., veg18, veg19), rename them to a common name (e.g., veg) in each year’s list before passing to stack_yearly_tables().

# Example: standardise table names before stacking
RICA_18_raw_std <- stats::setNames(
  RICA_18_raw,
  gsub("18$", "", names(RICA_18_raw))
)
# "veg18" becomes "veg", "ani18" becomes "ani", etc.

How the pivot works internally

The function pivot_national_fadn() performs the following for each product group (using CROPS / veg as example):

# --- Internal logic (pseudo-code, using CROPS as example) ---

# 1. Read which national columns to pivot from variable_pattern
#    For CROPS: SUPER3, SUPIR3, QPROD3, QVENT3, VAUTO3, VINT, VPBRT3,
#               VSTOD3, VSTOF3, VVENT3
crop_suffixes <- dict_conversion$variable_pattern %>%
  filter(Group == "CROPS", !is.na(pattern_national)) %>%
  select(pattern_national, pattern_FADN, unit_conversion)

# 2. Read category mapping (many-to-one allowed)
#    111 -> CWHTC, 115 -> CBRL, 116 -> CBRL, ...
crop_categories <- dict_conversion$category_pattern %>%
  filter(Group == "CROPS") %>%
  select(national_code, FADN_code_letter, allocation_key)

# 3. Identify numeric value columns, then summarise by farm × year × crop
#    This collapses production modes or duplicate rows within a farm-crop
group_cols  <- c("IDENT", "YEAR", "CODE3")
value_cols  <- setdiff(
  names(raw_tables$veg %>% select(where(is.numeric))),
  group_cols
)

veg_summed <- raw_tables$veg %>%
  summarise(
    across(all_of(value_cols), ~ sum(.x, na.rm = TRUE)),
    .by = all_of(group_cols)
  )

# 4. Pivot LONGER: one row per farm × year × crop × variable
#    This is the key difference from a direct pivot_wider approach —
#    going long first allows dictionary-driven joins
veg_long <- veg_summed %>%
  pivot_longer(
    cols      = all_of(value_cols),
    names_to  = "pattern_national",
    values_to = "value"
  ) %>%
  mutate(CODE3 = as.character(CODE3))
# Columns: IDENT, YEAR, CODE3, pattern_national, value
# e.g.:    FARM_0001, 2020, 111, SUPER3, 12.5

# 5. Join the FADN prefix (category mapping)
#    CODE3 "111" → FADN_code_letter "CWHTC", allocation_key 1
#    CODE3 "115" → FADN_code_letter "CBRL",  allocation_key 1
#    CODE3 "116" → FADN_code_letter "CBRL",  allocation_key 1
veg_long <- veg_long %>%
  left_join(crop_categories, by = c("CODE3" = "national_code"))

# 6. Join the FADN suffix (variable mapping) + unit conversion
#    pattern_national "SUPER3" → pattern_FADN "TA", unit_conversion 0.01
#    pattern_national "QPROD3" → pattern_FADN "PRQ", unit_conversion 0.01
veg_long <- veg_long %>%
  left_join(crop_suffixes, by = "pattern_national")

# 7. Aggregate: sum value × allocation_key × unit_conversion
#    This is where many-to-one categories are collapsed:
#    CBRL_TA = sum of (115_SUPER3 × 1 × 0.01) + (116_SUPER3 × 1 × 0.01)
#    Allocation keys allow splitting shared categories (e.g., eggs)
veg_summed_fadn <- veg_long %>%
  filter(!is.na(pattern_FADN), !is.na(FADN_code_letter)) %>%
  summarise(
    value = sum(value * allocation_key * unit_conversion, na.rm = TRUE),
    .by = c("IDENT", "YEAR", "FADN_code_letter", "pattern_FADN")
  )
# e.g.: FARM_0001, 2020, CWHTC, TA, 0.125
#        FARM_0001, 2020, CBRL,  TA, 0.340  (sum of 115 + 116)

# 8. Pivot WIDER: one row per farm-year, FADN-named columns
veg_final <- veg_summed_fadn %>%
  pivot_wider(
    id_cols     = c("IDENT", "YEAR"),
    names_from  = c("FADN_code_letter", "pattern_FADN"),
    values_from = value,
    values_fill = NA_real_
  )
# Columns: IDENT, YEAR, CWHTC_TA, CWHTC_PRQ, CBRL_TA, CBRL_PRQ, ...

Manual matches: farm-level variables

After all product groups are pivoted and joined, farm-level variables from the main national table are added via the manual_matches dictionary sheet. The function detects the column type automatically:


# --- Manual match logic (pseudo-code) ---

# Character/factor columns (e.g., REGIO → NUTS2, OTEXE → TF14)
#   → take first non-NA value per farm-year (no numeric conversion)
raw_tables$rica %>%
  summarise(NUTS2 = first(REGIO[!is.na(REGIO)]), .by = c(IDENT, YEAR))

# Numeric columns (e.g., SAUTI → SE025, UTANSP → SE010)
#   → sum with unit conversion factor
raw_tables$rica %>%
  summarise(SE025 = sum(SAUTI * 1, na.rm = TRUE), .by = c(IDENT, YEAR))

# Redundant id mappings (e.g., IDENT → ID when IDENT is in id_cols)
#   → automatically skipped to avoid nonsensical aggregation

Summary of the pivot strategy

Step Operation Purpose
1–2 Read dictionary sheets Load suffix map, category map, unit conversions
3 summarise(.by = farm × crop) Collapse duplicate rows (e.g., production modes)
4 pivot_longer() One row per farm × crop × variable (join-ready)
5 left_join(categories) Attach FADN prefix + allocation key
6 left_join(suffixes) Attach FADN suffix + unit conversion
7 summarise(value × key × conv) Aggregate many-to-one categories
8 pivot_wider() Final wide format: CWHTC_TA, CBRL_PRQ, …
9 Manual matches Add farm-level character & numeric variables

Handling special cases

Many national codes → one FADN code (aggregation)

Multiple RICA codes mapping to the same FADN code are summed automatically.

RICA          FADN
115 (winter barley)  ─┐
116 (spring barley)  ─┼──► CBRL  (barley)
117 (escourgeon)     ─┘

The pivoted columns 115_SUPER3, 116_SUPER3, 117_SUPER3 are summed into CBRL_TA.

One national code → many FADN codes (allocation)

When one RICA code must be split across multiple FADN codes, add an allocation_key in the category_pattern sheet:

FADN_code_letter national_code Group allocation_key
PEGGCONS 76 ANIMAL PRODUCTS AND SERVICES 0.95
PEGGHATCH 76 ANIMAL PRODUCTS AND SERVICES 0.05

The pivoted value for code 76 will be multiplied by the allocation key.

RICA-specific unit quirks (livestock)

Some RICA variables encode units differently depending on the product code. These are handled via code-specific conversion factors declared in the category_pattern sheet or via a dedicated unit_conversion sheet:

national_code pattern_national conversion_factor notes
911:965 EFFEC6 0.1 tenths of head → heads
974;975;983;984 EFFEC6 100000 ten-thousandths → heads
993 EFFEC6 10 tens of hives → hives
974;975;983;984 QPBRT6 1000 thousands → units

These are applied before pivoting in pivot_national_fadn().

FADN suffixes with no RICA equivalent

Rows in variable_pattern where pattern_national is empty (e.g., A, ENA, GM, ENTA, IRA, ALU, PI, SSN, SSV, SRN, SRV, NO, FCN, FCV, FUN, FUV for livestock) will produce NA columns in the output. These can be computed downstream if data is available from other sources.

Tips

  • Start with variable_pattern: even a dozen suffix rows generate hundreds of variable mappings when crossed with the category codes.
  • The Group column is the join key between the two tables. It must match exactly: CROPS, LIVESTOCK, or ANIMAL PRODUCTS AND SERVICES.
  • Version-control your dictionary: the Excel file is the single source of truth. Track it alongside your code.
  • Re-use across years: once built for one year, only minor updates are usually needed for subsequent years.
  • Use validate_dictionary() after every edit: it catches missing mappings, invalid conversion factors, and orphaned category codes before they become silent NA in your results.
